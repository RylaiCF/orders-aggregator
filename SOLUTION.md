# Решение тестового задания: Orders Aggregator

## 1. Что сделано и какие решения приняты

В рамках доработки сервиса агрегации заказов были решены две основные задачи: внедрение учета скидок во всей цепочке сервиса (от схемы БД до публичного API) и исправление ошибки отнесения заказов к календарным дням в таймзоне клиента в периоды перехода на сезонное время (DST).

### Основные архитектурные и технические решения:

1. **Хранение данных в БД (ADR 0002)**:
   - В таблицу `orders` миграцией `002_add_discounts.sql` добавлена колонка `amount_paid_kop BIGINT NOT NULL DEFAULT 0`.
   - Существующие исторические заказы смигрированы выражением `UPDATE orders SET amount_paid_kop = amount_kop;`.
   - **Решение**: сохранять только фактически уплаченную сумму (`amount_paid_kop`) и начальную стоимость (`amount_kop`) в целочисленных копейках. Величина скидки `discount` не хранится в БД, а вычисляется при агрегации как разность `gross - net`. Это исключает избыточность, рассинхронизацию данных и проблемы с накоплением погрешности при округлениях.

2. **Нормализация и прием данных (`OrdersService`)**:
   - Модель `ExternalOrder` расширена поддержкой полей `amountPaid` и `discountPercent` (как числовых, так и строковых значений, либо `null/undefined`).
   - Приоритет вычисления уплаченной суммы:
     - Если передан `amountPaid` — берется он.
     - Иначе, если передан `discountPercent` — уплаченная сумма вычисляется по формуле: `amount * (100 - discountPercent) / 100`.
     - Иначе (заказ без скидки или старый формат) — `amountPaid = amount`.
   - Все денежные суммы приводятся к копейкам на границе ввода с помощью функции `toKop`.

3. **Расчет статистики (`TotalsService`) и публичный API**:
   - Интерфейс `DailyTotal` расширен полями:
     - `gross`: сумма заказов до скидки в рублях;
     - `net`: фактически оплаченная клиентом сумма в рублях;
     - `discount`: разница `gross - net` в рублях;
     - `total`: сохранено для обратной совместимости (`= gross`).
   - Агрегация сумм ведется в копейках (`grossKop`, `netKop`), а `discountKop = grossKop - netKop` вычисляется перед переводом в рубли через `fromKop`, что гарантирует строгое равенство `gross === net + discount` без копеечных расхождений.
   - Дни без заказов в запрошенном диапазоне возвращаются с нулевыми суммами.

4. **Индивидуальное определение даты заказа в таймзоне клиента (ADR 0001)**:
   - Создана функция `orderDay(at: Date, timeZone: string): string` в `src/utils/time.ts` на базе нативного `Intl.DateTimeFormat`.
   - Каждый заказ при агрегации относится к календарному дню с учетом фактического смещения таймзоны клиента в момент создания заказа (`createdAt`).

## 2. Причина расхождения из жалобы аналитиков и как нашли

### Суть жалобы
По клиенту `c_7` за 27–31 марта 2026 года суммы по части дней расходились с отчетом платежной системы, хотя платежная система считает дни в таймзоне клиента.

### Точная причина
1. Клиент `c_7` находится в таймзоне `Europe/Berlin` (Германия).
2. В Германии в последнее воскресенье марта (в 2026 году это **29 марта 2026 года**) в 02:00 происходит переход на летнее время (DST): часы переводятся на 1 час вперед, смещение относительно UTC меняется с **CET (UTC+1)** на **CEST (UTC+2)**.
3. В исходной реализации сервиса смещение вычислялось один раз для всего диапазона на основе текущего момента времени запуска сервера/запроса:
   ```ts
   const offset = tzOffsetMinutes(timezone, new Date());
   ```
   и затем применялось статически ко всем заказам:
   ```ts
   const date = dateAtOffset(o.createdAt, offset);
   ```
4. В результате:
   - Для заказа, созданного **29 марта 2026 года в 22:30 UTC**:
     - В реальном местном времени Берлина действует летнее время CEST (UTC+2), поэтому локальное время составляет `22:30 + 02:00 = 00:30` следующего дня — **30 марта 2026 года**.
     - При использовании статического зимнего смещения UTC+1 локальное время рассчитывалось как `22:30 + 01:00 = 23:30` того же дня — **29 марта 2026 года**.
   - Заказы, оформленные в интервале **22:00–23:00 UTC** после перехода на летнее время, ошибочно попадали в предыдущий календарный день, искажая итоги как за 29 марта, так и за 30 марта.

### Как нашли
- Проверили таймзону клиента `c_7` через API `/customers/c_7` — оказалась `Europe/Berlin`.
- Сопоставили указанный в жалобе интервал (конец марта, 27–31.03.2026) с астрономическим календарем перевода часов в ЕС: переход CET $\to$ CEST происходит именно 29 марта.
- Проанализировали код `src/services/totals.ts` и `src/utils/time.ts`: обнаружили использование единого статического `offset`, вычисляемого от `new Date()`.
- Изучили заказы клиента `c_7` в БД и подтвердили наличие заказов поздним вечером (между 22:00 и 23:00 UTC) 29 и 30 марта.

## 3. Что ещё заметили в коде или в поведении внешнего API

1. **Потеря точности IEEE-754 в `toKop`**:
   - В исходной функции `toKop(rub: number)` использовался `Math.floor(rub * 100)`.
   - В стандарте IEEE-754 для некоторых десятичных дробей возникает погрешность представления: например, `4723.9 * 100 === 472389.99999999994`. Применение `Math.floor` давало `472389` вместо `472390`, то есть терялась 1 копейка.
   - Было исправлено на `Math.floor(Math.round(rub * 1000) / 10)`, что полностью устраняет погрешность представления для сумм с двумя знаками после запятой и корректно отсекает субкопеечные доли.

2. **Особенности rate limiting во внешнем API**:
   - Внешний API имеет ограничение 5 rps. При превышении он может вернуть не только стандартный статус `429 Too Many Requests` (иногда без заголовка `Retry-After`), но и `200 OK` с JSON-телом `{ "error": "rate_limited" }`.
   - В клиенте `HttpOrdersApi` реализован троттлинг на 4 rps и экспоненциальный backoff с распознаванием обоих форматов rate limit.

3. **Особенности пагинации внешнего API**:
   - При достижении конца списка заказов внешний API не всегда выставляет `nextCursor: null`, а возвращает пустую страницу (`items: []`) с тем же самым курсором. В `SyncService` предусмотрена защита от бесконечного цикла по признакам `items.length === 0` и `seen.has(cursor)`.

4. **Неоднородность формата данных**:
   - В исторических заказах поля `amountPaid` и `discountPercent` отсутствуют;
   - Числовые значения в API могут приходить как числами, так и строками (например, `"4419.00"`), что потребовало гибкой валидации в Zod.

## 4. Какие допущения сделали там, где требования неоднозначны

1. **Приоритет `amountPaid` перед `discountPercent`**:
   - Если во входном объекте заказа переданы одновременно и `amountPaid`, и `discountPercent`, сервис берет значение `amountPaid`, поскольку это первичный платежный факт. Расчет через процент используется только при отсутствии `amountPaid`.
2. **Округление и расчет скидки**:
   - Скидка вычисляется на уровне агрегатов как `grossKop - netKop`. Это исключает расхождения вида `gross !== net + discount` из-за независимого округления трех величин.
3. **Дни без активности**:
   - Для всех календарных дней диапазона `from..to`, в которых не было оплаченных заказов, возвращаются записи с нулевыми суммами (`total: 0, gross: 0, discount: 0, net: 0`).
4. **Обратная совместимость `total`**:
   - Поле `total` сохранено и строго равно `gross` (сумме до скидок), согласно требованиям ТЗ.

## 6. Что бы доделали при наличии времени

1. **Группировка на уровне базы данных (SQL)**:
   - В текущей реализации сервис извлекает заказы за диапазон с запасом $\pm 1$ день и группирует их в памяти Node.js через `orderDay`.
   - При росте объема данных до десятков миллионов заказов эффективнее выполнять агрегацию прямо в PostgreSQL с помощью `created_at AT TIME ZONE timezone` и составного индекса `(customer_id, created_at)`.
2. **Асинхронная обработка и очереди**:
   - Перевод долгой синхронизации (`POST /sync`) на фоновые воркеры (на базе BullMQ или Kafka) с отдачей `202 Accepted` и polling/webhook уведомлением о завершении.
   - Очередь для обработки входящих вебхуков с гарантией порядка и dead-letter queue (DLQ) при сбоях.
3. **Распределенная идемпотентность**:
   - Использование `pg_advisory_xact_lock` для предотвращения параллельных запусков синхронизации между несколькими репликами сервиса.
4. **Кэширование справочников**:
   - Кэширование таймзон клиентов в Redis с TTL, чтобы снизить число запросов к эндпоинту `/customers/:id`.
5. **Наблюдаемость и мониторинг**:
   - Внедрение OpenTelemetry для трассировки запросов к внешнему API и метрик Prometheus (latency, upstream error rate, rate limit occurrences).
